# Персональный ИИ-наставник — концепция и архитектура (Этап 1)

Статус: **основные решения приняты** (см. §13), идёт подготовка Фазы 0. Код не пишется до финального подтверждения плана.
Стек: **клиент — Kotlin (Android)**, **бэкенд — Rust**, **ИИ — локальные самохостируемые модели** (без внешних AI-сервисов). Подробно про ИИ-стек: [ai-local-stack.md](ai-local-stack.md).

---

## 1. Суть продукта в одном абзаце

Это не чат-бот, не календарь и не трекер привычек. Это **персональная интеллектуальная система**: наставник-персонаж постепенно узнаёт человека, помогает ставить цели, превращает их в реалистичные планы, распределяет задачи по расписанию, честно проверяет выполнение, замечает закономерности поведения и постепенно учит пользователя управлять своей жизнью самостоятельно. Ключевой критерий качества любого решения: **«помогает ли это человеку стать самостоятельнее?»**, а не «увеличивает ли это время в приложении?».

## 2. Продуктовые принципы (влияют на архитектуру)

1. **ИИ — ядро, остальное — его инструменты.** Экраны и трекеры обслуживают наставника, а не наоборот.
2. **Честность.** История пропусков не переписывается; проверка никогда не называется «100%», если это не так; пользователь всегда видит, *каким способом* подтверждено выполнение.
3. **Реалистичность.** Планировщик обязан учитывать реальную нагрузку и не создавать невозможные расписания.
4. **Приватность по умолчанию.** Камера/микрофон — только с разрешения; видео не покидает устройство; лишние данные не собираются; «забудь тему X» — реальное удаление, включая копии. **Диалоги обрабатываются локально/на своём сервере — внешним AI-сервисам не передаются.**
5. **Безопасность подростков.** Без диагнозов, манипуляций, давления, чувства вины; кризисные темы → поддержка + рекомендация доверенного взрослого/специалиста.
6. **Стоимость под контролем.** Простые алгоритмические операции (конфликты расписания, таймеры, XP, проверка правдоподобия времени) **не должны** использовать нейросеть.

| 13 | **Privacy & Data Control** | Управление памятью, экспорт, удаление аккаунта и копий, согласия (камера/микрофон) | Нет |

## 4. Общая архитектура

```
┌─────────────────────────── Android (Kotlin) ───────────────────────────┐
│  UI (Jetpack Compose): Главная · Чат · Цели · Расписание · Отчёты      │
│  Mentor View: персонаж (ассеты: изображения/анимации, эмоции/позы)     │
│  Локальное: Room (кэш), DataStore, фото прогресса (ТОЛЬКО на устройстве)│
│  Проверки на устройстве: CameraX + MediaPipe Pose (подсчёт повторений), │
│     ML Kit OCR, таймеры, квизы, запись голоса                           │
│  WorkManager (напоминания/фон), FCM (push), виджеты, deep links         │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ HTTPS + JWT, стриминг (SSE)
┌───────────────────────────────▼────────────────────────────────────────┐
│                    Backend (Rust) — модульный монолит                   │
│  modules: auth │ persona │ chat │ memory │ goals │ schedule │ tasks     │
│           verification │ analytics │ content │ notifications │          │
│           gamification │ reports │ privacy                             │
│  AI Orchestration: роутинг намерений → сбор контекста → промпт →        │
│     LLM → структурированные «действия» → подтверждение → транзакция     │
│  Job scheduler (сводки, консолидация памяти, эскалации, отчёты)         │
└───────┬──────────────────────┬──────────────────────┬───────────────────┘
        │                      │                      │
 PostgreSQL 16            Redis            Локальный рантайм LLM
 + pgvector           (сессии, кэш,       (llama.cpp / Ollama,
 (source of truth,     очереди)            OpenAI-совместимый API;
  память, факты)                           см. ai-local-stack.md)
```

**Важные решения:**

- **Модульный монолит, а не микросервисы.** На старте это критично: меньше инфраструктуры, транзакционность между модулями (задача + напоминание + XP — одной транзакцией). Модули общаются через внутренние интерфейсы, что позволит при росте выделить нагруженные части.
- **Все изменения данных ИИ делает только через структурированные действия.** LLM не пишет в БД напрямую: она возвращает JSON-действие («создать задачу», «предложить перенос»), которое система показывает пользователю и выполняет после подтверждения. Это и безопасность, и честность.
- **Конфликты расписания, таймеры, XP, проверка правдоподобия — чистый код на Rust.** Нейросеть вызывается только там, где нужен язык/анализ.
- **Локальные модели.** Диалоги не покидают нашу инфраструктуру: модель работает на ноутбуке (разработка), далее на нашем VPS. Путь роста и ограничения — в [ai-local-stack.md](ai-local-stack.md).

### Распределение «сервер ↔ устройство»

| На сервере | На устройстве |
|-----------|---------------|
| Аккаунты, синхронизация, БД, история | UI, персонаж, анимации |
| Оркестрация ИИ (локальная LLM), промпты, память | Камера, микрофон (с согласия) |
| Логика расписания, задач, XP, отчётов | Компьютерное зрение (подсчёт повторений — локально) |
| Диспетчер уведомлений (FCM) | Таймеры, квизы, локальные напоминания |
| Модерация и safety-фильтры | Фото прогресса (не уходят на сервер по умолчанию) |

## 5. ИИ-наставник: варианты реализации

> **Принято: Вариант C — самохостинг открытых моделей.** Требование заказчика: не зависеть от внешних сервисов, целевая точка — «своя нейросеть». Сейчас всё крутится локально на ноутбуке (Windows, Intel Core i7, встроенная графика), далее переезжает на VPS. Слой `LlmProvider` сохраняется (OpenAI-совместимый API локального рантайма), поэтому смена моделей и миграция на VPS/GPU не потребуют переписывания домена. Модели, скорости, ограничения и путь к собственной дообученной модели — в [ai-local-stack.md](ai-local-stack.md). Варианты A и B ниже оставлены для справки и как «план Б».

### Вариант A — облачный LLM API (справочно)
Каждый смысловой вызов идёт в облачную модель через слой абстракции `LlmProvider`.
- **Плюсы:** лучшее качество диалога и понимания, минимум инфраструктуры, быстрый старт.
- **Минусы:** зависимость от провайдера (противоречит требованию независимости), приватность диалогов у третьей стороны.

### Вариант B — гибрид (справочно)
Лёгкая локальная модель (классификация намерений, извлечение сущностей) + облако для генерации. Та же зависимость от провайдера — не подходит как основной сценарий.

### Вариант C — самохостинг открытых моделей (принято)
Своя инфраструктура: llama.cpp / Ollama (OpenAI-совместимый API) + открытые модели (Qwen3, Gemma 3 и др.).
- **Плюсы:** полная независимость, контроль над данными, предсказуемая себестоимость, путь к собственной дообученной модели (LoRA).
- **Минусы (честно):** качество диалога и скорость ниже, чем у облачных флагманов; нужны ОЗУ/GPU и немного ML-ops. Детали и митигации — в [ai-local-stack.md](ai-local-stack.md).

### Конвейер одного сообщения
1. **Роутинг намерений** (правила/маленькая модель): свободный чат · планирование · обучение · отчёт · изменение данных · кризисный контент.
2. **Сбор контекста:** профиль + долгосрочная память (семантический поиск по фактам) + сегодняшнее расписание + активные задачи + окно диалога + стиль выбранного персонажа.
3. **Генерация** с промпт-шаблоном персонажа (версионируемые шаблоны, few-shot примеры характера — особенно важны для малых моделей).
4. **Пост-обработка:** safety-модерация, извлечение «действий», извлечение фактов для памяти.
5. **Выполнение действий** — только после явного подтверждения пользователя (кроме безобидных вроде «запомнить предпочтение»).

### Инициативные диалоги (проактивный движок)
Планировщик задач на сервере триггерит события: «утренняя сводка», «вечерний итог», «заметил паттерн прокрастинации», «проверка актуальности устаревших событий». Триггер собирает фактуру → LLM персонализирует текст (в фоне, локально) → push с учётом настроек активности пользователя (можно всё выключить). Жёсткие правила против спама: лимит инициативных сообщений в день, дедупликация, не более N напоминаний по одной задаче.

## 6. Система памяти

| Уровень | Содержание | Хранение | Срок |
|---------|-----------|----------|------|
| **L1 · рабочая** | Текущий диалог, активные задачи разговора | Postgres + Redis | окно ~последних N сообщений |
| **L2 · долгосрочная** | Факты о пользователе: интересы, привычки, цели, предпочтения («любит преподавателя X на YouTube»), устойчивые особенности | таблица `memory_facts` + эмбеддинги (pgvector) | пока не устареет/не удалит пользователь |
| **L3 · контекстная** | Временные обстоятельства: перенос занятия, «на этой неделе сессия», болезнь | `context_events` с TTL/привязкой к датам | истекает автоматически |

**Консолидация (фоновая, например ночью):** диалоги → извлечение кандидатов-фактов (локальная LLM, пачками) → дедупликация/слияние с существующими → признак «важности» и «уверенности». Выводы аналитики (паттерны) хранятся отдельно со ссылкой на **реальные наблюдения** («за 3 недели 8 из 10 переносов были вечерних занятий»), а не как голословные утверждения. Эмбеддинги считаются локальной моделью (bge-m3) — внешние сервисы не нужны.

**Поток «забудь тему X»:**
1. Семантический + структурный поиск затронутых записей (факты, события, фрагменты диалогов, настройки).
2. Пользователю показывается **конкретный список** — что именно будет удалено/изменено.
3. Явное подтверждение.
4. Удаление из основной БД + постановка tombstone.
5. **Реальное удаление из копий:** бэкапы — ротационные; удалённые записи вычищаются при следующей ротации и при восстановлении (восстановление сверяется с tombstone). Это делается явной фоновой задачей, а не «скрытием записи из UI».
6. Пользователь видит обновлённую память (экран «О чём ты меня знаешь»).

Чувствительные темы помечаются `sensitive=true`: учитываются при планировании, но не поднимаются наставником без причины.

## 7. Система проверки выполнения заданий

**Принцип:** метод проверки выбирается при создании задачи (ИИ + конфигурация) из **реестра верификаторов (плагинная архитектура)**; тяжесть метода пропорциональна важности задачи; пользователь всегда видит уровень проверки. Приоритет методов Фазы 2 выбирается после MVP.

| Метод | Как работает | Где считается | Этап |
|-------|-------------|--------------|------|
| **Таймер** | Факт затраченного времени, сессия фокуса | устройство | MVP |
| **Самоподтверждение** | Явное действие пользователя | устройство | MVP |
| **Квиз/тест** | Встроенные вопросы, проверка ответов | сервер/устройство | MVP |
| **Правдоподобие времени** | Алгоритмические пороги («10 страниц за 20 секунд» → не принимаем молча) | сервер, без ИИ | MVP |
| **Фото + OCR/LLM-ревью** | Фото страницы/проекта → извлечение текста → вдумчивая проверка (локальной LLM) | OCR на устройстве, ревью — сервер | Фаза 2 |
| **Голос** | Устные ответы, разговорная практика | whisper.cpp локально | Фаза 3 |
| **Камера + CV** | Распознавание движений, подсчёт повторений (MediaPipe Pose) | **только на устройстве**; на сервер идут лишь «сделано N повторений» | Фаза 2–3 |
| **Код** | Запуск и проверка кода пользователя в песочнице (WASM/контейнер, лимиты CPU/RAM/времени) | сервер | Фаза 3 |

**Правила честности (заложены в модель данных):**
- У каждого подтверждения — уровень: `подтверждено` (объективно) · `проверено с высокой вероятностью` (ИИ/алгоритм) · `самоподтверждено`. UI показывает уровень **явно**, без преувеличений.
- **Система надёжности:** добросовестная история подтверждений может ослаблять проверку для простых действий (это про удобство, а не про оценку личности — формулировки в UI нейтральные).
- Камера — только с разрешения; для упражнений можно кадрировать так, чтобы лицо не было в кадре; видео **не сохраняется и не отправляется** по умолчанию.
- Если проверка технически невозможна — система честно предлагает альтернативу (другой метод или пониженный уровень).

## 8. Расписание: постоянное + временные исключения

Модель данных (сервер, чистый алгоритм):
- `schedule_rule` — повторяющееся событие (RRULE-подобное: «вт/чт 17:00, 60 мин»).
- `schedule_exception` — **одноразовая** инстанс-замена: перенос/отмена конкретной даты, с датой истечения.
- После завершённого переноса исключение истекает само → постоянное правило продолжает действовать.

Запрос «учитель переносит на субботу 12:00» обрабатывается так: ИИ парсит фразу → структурированная команда → движок расписания проверяет конфликты (пересечения интервалов) → показывает пользователю результат («в субботу 12:00 свободно, но в 13:30 у тебя спорт») → после «да» создаётся исключение. Никогда: молча создать пересечение; навсегда изменить правило из-за разового переноса. Устаревшие события («ещё актуально?») — фоновая проверка.

Недельный вид в приложении: слоями — постоянные занятия + поверх временные изменения, с визуальным отличием.

## 9. Технологический стек (предложение)

### Android (Kotlin)
| Слой | Технология | Зачем |
|------|-----------|-------|
| UI | Jetpack Compose, Material 3 | Минимализм «в духе Apple», декларативность |
| Архитектура | MVI/MVVM + модульность (feature-модули) | Не ломать работающее при добавлении функций |
| DI | Hilt | Стандарт |
| Данные | Room (кэш), DataStore, WorkManager | Синхронизация, фон |
| Сеть | Retrofit/OkHttp + SSE-клиент | Стриминг ответов наставника |
| Персонаж | Слой `MentorView` поверх абстракции ассетов (Lottie/спрайты/статика) | Арт подключается отдельно, без переписывания (пока заглушки) |
| Проверки | CameraX + MediaPipe Tasks (Pose), ML Kit OCR | Локальное CV |
| Push | FCM | Уведомления |
| Прочее | Biometric, Security-crypto | Защита локальных данных |

### Backend (Rust)
| Слой | Технология | Зачем |
|------|-----------|-------|
| HTTP | **Axum** + Tower | Зрелая экосистема Tokio, асинхронность |
| БД | **PostgreSQL 16** + **SQLx** (миграции), **pgvector** | Единый source of truth + семантическая память |
| Кэш/очереди | Redis | Сессии, rate-limit, очередь фоновых задач |
| Авторизация | JWT (access+refresh), **argon2id** | Стандарт безопасности |
| AI-слой | Своя абстракция `LlmProvider` (OpenAI-совместимый HTTP) | Независимость от рантайма и модели |
| Модельный рантайм | **llama.cpp / Ollama** в Docker Compose (OpenAI-совместимый API) | Локальные модели, без внешних сервисов |
| Фоновые задачи | Tokio-планировщик в том же сервисе | Сводки, консолидация памяти, эскалации |
| Наблюдаемость | `tracing`, метрики, healthchecks | Без этого больно на проде |
| API-контракт | OpenAPI (`utoipa`) → генерация Kotlin-клиента | Клиент и сервер не разъезжаются |
| Деплой | Docker Compose, GitHub Actions CI | Просто и воспроизводимо; переезжает на VPS как есть |

**Честно о выборе Rust для бэкенда:** сильные стороны — производительность, надёжность, предсказуемое поведение сложной доменной логики (расписание, верификация), дешёвый хостинг. Слабые — меньше готовых AI/ML-SDK и медленнее итерации, чем на Go/Python. Для этого продукта приемлемо: все LLM-вызовы — обычные HTTP к локальному рантайму, а скорость итераций компенсируем модульным монолитом и генерацией клиента из OpenAPI.

**Dev-окружение (Windows):** WSL2 + Docker Desktop (Postgres, Redis, llama.cpp, backend), Rust в WSL2, Android Studio нативно, Ollama на Windows для пробы моделей. Подробнее — в [ai-local-stack.md](ai-local-stack.md).

## 10. Этапы разработки

**Фаза 0 · Фундамент** (несколько недель)
Каркас репозитория: Cargo workspace (модули backend) + Android-проект (feature-модули). CI, миграги, Docker Compose (Postgres+pgvector, Redis, llama.cpp, backend). Auth (логин/пароль, refresh-токены). Пустые «раковины» экранов. Подключение локальной LLM.

**Фаза 1 · MVP — «наставник, который работает»**
- Онбординг-знакомство: живой диалог с открытыми вопросами, первый профиль пользователя; отдельно — «есть ли уже конкретная цель».
- Выбор наставника (2–3 персонажа-заглушки, архитектура подключаемых ассетов), текстовый чат с памятью L1/L2.
- Цели: создание, декомпозиция ИИ на шаги, план; приоритизация нагрузки («и английский, и программирование, и спорт» → оценка и расстановка приоритетов).
- Задачи + проверки MVP-уровня: таймер, самоподтверждение, квизы, правдоподобие времени.
- Расписание: постоянные занятия, недельный вид, переносы через диалог (исключения).
- Напоминания с эскалацией (1 → повтор → пауза → обсуждение пропуска при следующем контакте; без спама).
- Геймификация: XP за подтверждённое, уровни, огонёк (без наказаний), 5–7 достижений.
- Еженедельный отчёт. Экран памяти («что ты обо мне знаешь») + «забудь тему».
- Safety-слой: модерация, кризисный сценарий, настройки активности наставника.

**Фаза 2 · Глубина**
Фото-проверки (OCR/LLM-ревью), камера+CV для упражнений (локально), поведенческая аналитика с выводами-паттернами, ежедневные/30-дневные отчёты, умные проверки актуальности событий, виджеты Android, базовые deep links, экспорт данных.

**Фаза 3 · Обучение и голос**
Подбор материалов из интернета (YouTube/статьи/курсы) с персонализацией и запоминанием преподавателей; проверка кода в песочнице; голосовые сообщения и голосовые диалоги (whisper.cpp + Piper — локально); расширенные эмоции/анимация персонажа.

**Фаза 4 · Расширение**
iOS (Kotlin Multiplatform для общих слоёв или отдельный клиент — решение позже), браузерная версия, календари/фитнес-интеграции, соцфункции, видеозвонок с персонажем, **LoRA-дообучение своей модели наставника** (см. ai-local-stack.md, §5).

## 11. MVP — критерий готовности

«Настоящий MVP» = пользователь проходит полный цикл:
**знакомство → цель → план → задачи в расписании → напоминания → проверка выполнения → обратная связь наставника → недельный отчёт → рост уровня.**
Всё, что не обслуживает этот цикл, — за бортом MVP (камера, голос, контент-поиск, соцфункции, виджеты).

## 12. Риски (технические и финансовые)

| Риск | Влияние | Митигация |
|------|---------|-----------|
| **Качество и скорость локальных моделей** (диалог слабее облачных флагманов, ответы медленнее на CPU) | UX наставника | Стриминг, сильные промпт-шаблоны + few-shot характер, структурированные действия, RAG; путь роста: GPU VPS → LoRA-дообучение своей модели |
| **Ограничения железа ноутбука** (ОЗУ, один пользователь) | Темп разработки, нагрузка | Модель под ОЗУ (4B при 8 ГБ), фоновые задачи пачками; переход на VPS без переписывания (абстракция `LlmProvider`) |
| **Эксплуатация самохостинга** (обновление моделей, мониторинг, бэкапы) | ML-ops время | Всё в Docker Compose, скрипты обновления, документированные runbook'и |
| **Безопасность подростков / модерация** | Репутационный и юридический | Safety-фильтры, кризисный протокол, возрастной гейт в сторах, минимум персональных данных |
| **Надёжность push на Android** (Doze, «убийцы» от OEM) | Напоминания не доходят → продукт не работает | WorkManager + exact alarms для важного, onboarding-просьба отключить оптимизацию батареи, in-app дублирование |
| **Точность CV** на разнородных Android | Фрустрация при проверке упражнений | CV только для простых движений (приседания/отжимания), честные уровни проверки, всегда есть альтернатива |
| **Темп разработки на Rust** (мало людей, меньше готового) | Дольше до релиза | Модульный монолит, узкие внутренние интерфейсы, генерация клиента из OpenAPI |
| **Реальное удаление данных из бэкапов** | Compliance, доверие | Tombstone + явная чистка при ротации/восстановлении, документированная политика ретеншна |
| **Продуктовый риск зависимости** | Против главной цели продукта | Принцип «учим самостоятельности» в метриках: успех = достижение целей, а не screen time; настройки инициативности |

## 13. Решения и следующий шаг

**Решения (по итогам обсуждения):**
1. **ИИ — самохостинг локальных открытых моделей** (независимость от внешних сервисов): старт на ноутбуке (Windows, Core i7, iGPU), далее VPS; цель — собственная дообученная (LoRA) модель наставника. Ограничения и план: [ai-local-stack.md](ai-local-stack.md).
2. **Инфраструктура — VPS**, переносимый Docker-стек (Docker Compose).
3. **Проверки заданий — плагинная архитектура** реестра верификаторов; приоритет методов Фазы 2 выбираем после MVP.
4. **Персонажи — заглушки** + слой подключаемых ассетов (изображения/эмоции/позы/анимация) под будущий арт.

**Следующий шаг (Фаза 0, после подтверждения):** каркас репозитория — Cargo workspace (backend-модули) + Android-проект (feature-модули) + `docker-compose.yml` (Postgres 16 + pgvector, Redis, llama.cpp, backend) + модуль auth (логин/пароль, JWT) + подключение локальной LLM к `LlmProvider`. Параллельно — схема БД и короткий RFC по AI-слою.
